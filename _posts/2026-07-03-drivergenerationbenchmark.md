# 把 Mock 测试重构成 Driver Generation Benchmark

最近我做了一轮不算小的重构：把一批原本只是“能跑”的 Linux 驱动 mock 测试，整理成了一套更
像 benchmark 的评测链路。

这件事表面上看像是在改测试格式，实际上不是。它真正解决的问题是：如果我想评估一个 agent
生成 Linux 驱动的能力，那么我不能只靠一些临时 shell 脚本、人工经验和零散日志。我需要一
套可以批量运行、统一汇总、对外解释得清楚的评测体系。

这篇文章按过程讲清楚这次重构是怎么做的，也解释为什么我最后会把整个方案收敛到一个很小的
`cases.json` 格式上。

## 先说背景：什么是 driver generation benchmark

如果读者平时不做内核开发，这里先补一句背景。

Linux 驱动的作用，是让内核知道怎样和具体硬件交互。对于一个传感器、电源芯片、触摸芯片或
者 PMIC，驱动要负责识别设备、配置寄存器、暴露用户态接口、处理错误情况，有时还要处理中
断、FIFO、状态切换等逻辑。

所谓 **driver generation benchmark**，就是给一个代码生成系统或者 agent 一份任务输入，让
它自动生成驱动代码，然后用统一的方式验证这份代码到底对不对。

这里最难的地方不在“让模型写代码”，而在“怎样定义一个公平、稳定、可重复的验证过程”。因为
如果评测本身是混乱的，那么最后得到的结论也不会可靠。

## 我最开始遇到的问题，不是没有测试，而是测试太像手工脚本

我手里一开始并不缺测试。

很多驱动已经有 mock 设备，也能在 QEMU 里启动 guest，然后靠 shell 脚本去加载模块、读写
sysfs、检查 debugfs、观察日志。这些东西对人工调试非常有用，因为写脚本的人知道上下文，也
知道失败时该怎么看。

但这种测试不适合直接拿来做 benchmark，原因很简单：

- 环境准备和断言逻辑混在一起
- 不同驱动的脚本风格不一致
- 失败日志难以统一汇总
- 批量运行时很难比较结果
- 很多隐式前提只存在于作者脑子里

也就是说，这类测试能帮人 debug，但不能稳定地评估 agent。

benchmark 需要的不是“某个脚本跑通了”，而是：

1. 输入格式统一
2. 执行方式统一
3. 输出总结统一
4. 失败原因可归类
5. 不依赖人工阅读大量日志

所以这次重构的第一原则，不是多写脚本，而是先把“测试到底是什么”重新定义清楚。

## 我最后没有设计复杂 DSL，而是选了最小测试原子

一开始我也想过把测试设计成很结构化的形式，比如：

- `op=read`
- `path=/sys/...`
- `save_as=xxx`
- `compare=...`

看起来很工整，但很快就发现这套东西没有真正解决问题，它只是在重复发明 shell。

因为在 guest 里，绝大多数测试动作本质上就是一条命令：

- `cat`
- `echo`
- `grep`
- `test`
- `dmesg`
- `insmod`
- `rmmod`

既然 shell 本身已经是一个足够通用的执行层，那么最小测试用例就不应该再套一层伪语言。最后
我把单个 case 收敛成了四个核心字段：

- `id`
- `cmd`
- `expect.exit`
- `expect.output`

也就是：给一条命令，执行它，然后检查退出码和输出。

一个最小例子大概长这样：

```json
{
    "id": "name_matches",
    "cmd": "cat \"$DEV/name\"",
        "expect": {
            "exit": 0,
            "output": "^chip-name$"
        }
}
```

这个设计看起来朴素，但它有几个很重要的优点。

第一，表达能力够强。
读文件、写文件、检查节点、匹配正则、验证失败路径，都能靠一条命令表达。

第二，执行模型统一。
无论是正常功能测试还是负例测试，runner 都只做一件事：执行命令，检查结果。

第三，不容易过拟合某一种驱动。
只要 guest 里 shell 能做，case 就能表达，不需要为了某个驱动多发明一类专用字段。

## 为什么同时保留 exit 和 output

这里我中间和自己反复争了一轮，最后结论是：exit 和 output 必须同时保留。

原因不复杂，它们回答的是两个不同问题。

exit 回答的是：命令整体是否成功。
output 回答的是：命令输出的内容是否符合预期。

举个例子：

- 读 name 文件时，命令可能成功，但设备名不对
- 写只读节点时，命令应该失败，但仅仅失败还不够，报错内容也可能需要检查
- 某些负例里，非零退出码是预期行为，不应该算测试失败

如果只看退出码，会漏掉“执行成功但结果错误”的情况。
如果只看输出，又会漏掉“输出看起来像对了，但实际命令失败”的情况。

所以这两个维度不能混成一个字段。benchmark 一旦走向批量化和自动汇总，就必须把它们显式分
开。

## 我把 runtime 测试分成了三类，再配一个 setup

在 case 原子稳定以后，整个驱动的运行时测试文件也就自然收敛出来了。

我最后采用的是一个很简单的组织方式：

- setup
- smoke
- functional
- negative

其中 setup 不是测试，它只是准备条件。比如：

- 加载 mock 模块
- 加载目标驱动
- 找到 sysfs 路径
- 导出环境变量

真正的测试只在后三组里。

### Smoke：先回答“它是不是活着”

smoke 测试不负责验证功能细节，它只负责确认最基本的运行状态已经成立。比如：

- 模块能否加载
- 设备是否成功绑定
- 用户态接口是否出现
- debugfs 或 sysfs 入口是否可见
- 内核有没有立刻爆 fatal error

这是最基础的一层。一个驱动如果连 smoke 都过不了，就没有必要继续跑更细的行为测试。

### Functional：验证正常功能语义

functional 测试才开始检查驱动“做得对不对”。

例如：

- name 是否正确
- raw / scale 的读取值是否符合预期
- 写入注入接口后寄存器是否变化
- trace 是否记录到了预期事件
- FIFO 是否产生数据
- IRQ 计数是否变化

这部分才真正接近“驱动功能正确性”。

### Negative：验证错误路径和恢复能力

negative 测试和 functional 用同一种格式，没有必要分两套 schema。

它们检查的内容通常包括：

- 向只读节点写入是否被拒绝
- 非法输入是否返回失败
- 模块卸载再重载后是否恢复
- 错误配置是否不会把状态带坏

这类测试很重要，因为很多生成模型喜欢把“正常路径能跑通”当成完成，但内核驱动不是普通脚
本，错误路径同样是接口契约的一部分。

## 统一格式不是终点，统一 runner 才是终点

把 case 写进 cases.json 只是第一步。真正让它变成 benchmark 的，是 runner。

如果没有 runner，cases.json 只是一个比较整齐的数据文件，最后还是要靠人去解释、去执行、
去看日志。这样并没有本质进步。

所以我后面做的事情，是写一个只服务于 cases.json 的 runner。它负责：

1. 读取 setup / smoke / functional / negative
2. 生成 guest 内部执行脚本
3. 启动 QEMU 或运行目标环境
4. 顺序执行测试
5. 解析串口日志
6. 输出统一 summary

这一步的意义很大，因为从这里开始，测试不再依赖“作者会不会写漂亮 shell”，而是依赖共同的
执行协议。

一旦有了统一 runner，就可以给每个驱动产出统一的总结，例如：

- compile 是否成功
- static 是否成功
- smoke 是否成功
- functional 是否成功
- negative 是否成功
- 每个 case 的 pass/fail
- 失败摘要
- 对应日志路径

这样才能真正批量跑一批驱动，再去比较不同 agent 或不同方法的结果。

## 输入池怎么定义，比很多人想的更重要

有了统一 runner 和 summary 以后，一个之前一直很难说清的问题终于可以被钉死：到底哪些驱动
应该进入 benchmark 输入池。

这一步看起来只是筛数据，实际上非常关键。因为 benchmark 的可信度，很大程度上取决于你怎么
定义样本。

我后来采用的标准很明确：

- 这个驱动支持 runtime 测试
- 新的 cases_summary 结果是 pass

满足这两个条件，就把它当作 runtime-green 驱动，纳入输入池。

这个判断标准的好处是它不依赖人工印象，也不依赖历史标签，而只依赖当前可重复验证的结果。

这里我中间还踩过一个坑：曾经额外叠加过更保守的历史过滤条件，导致输入池缩得太小。后来我
把这个定义改正了，因为 benchmark 的输入池应该服务于研究目标，而不是服务于“看起来更干
净”的错觉。

## 后来我把 benchmark 明确拆成 env、eval、public 三层

当测试体系开始稳定之后，另一个问题就变得必须面对：agent 到底能看到什么？

如果 agent 能直接看到正式评测用例，那这个 benchmark 很快就会退化成“谁更会适配题库”。这
不是我想要的。

所以我最后把整个 benchmark 边界分成三层：

- env：环境准备层
- eval：正式隐藏评测层
- public：公开自测层

### env

env 负责准备运行条件，比如：

- mock 怎么加载
- setup 怎么注入
- guest 里有哪些固定资源
- runner 怎样启动环境

这些信息对正式评测很重要，但不应该作为 solver 的任务输入直接暴露。

### eval

eval 是真正的 benchmark。
它包含隐藏测试、最终评分规则和正式 pass/fail 判定。

这部分必须对 agent 不可见，否则评测就会出现严重泄漏。

### public

public 只暴露有限的自测能力，让 agent 在开发阶段可以验证自己生成的代码是否大体合理，但
它看不到正式题库。

这一层我认为很有必要。因为完全不给自测手段，会让 agent 失去基本反馈渠道；但把正式测试全
给它看，又会破坏 benchmark 本身。

## 面向 agent 的输入，最后只保留了 task_brief 和 datasheet

测试边界理顺以后，任务输入也必须跟着收缩。

我最后倾向于只给 agent 两类信息：

- task_brief
- datasheet

task_brief 只是一小段简要描述，告诉 agent：这是一个什么设备，需要提供什么高层能力。

datasheet 则保留设备事实，例如：

- 寄存器映射
- bit 定义
- 读写语义
- 状态位
- 数据格式
- 初始化要求
- 时序和配置约束

这里刻意不放的东西包括：

- Linux 子系统名
- 现成 helper 名
- probe/remove 实现套路
- 相似驱动建议
- 任何接近“实现提示”的信息

原因很简单：我想测的是 agent 在公开信息下生成驱动的能力，而不是它根据隐藏提示拼装答案的
能力。

如果 agent 理解错需求，或者实现错功能，这两类错误在 benchmark 里都应该算错。现实开发中
它们也都算错。

## 任务构造后来走向了 GPT 批量生成，但这一步暴露了真实系统问题

当输入格式变成 task_brief + datasheet 以后，下一个自然问题就是：怎样为一批驱动批量构造
这两个字段？

我的做法是用 GPT 路径批量生成任务输入，让它根据已有资料和参考驱动，整理出面向 solver 的
公开任务描述。

这一步在小批量上是跑通了的，但也很快暴露出一个非常现实的问题：provider 的长尾延迟。

也就是说，链路是成立的，但全量吞吐并不稳定。少量样本能顺利生成，不代表一次性跑完整批驱
动就一定顺畅。

这件事其实挺值得记一笔，因为它提醒我：研究系统里的很多问题，不是算法问题，而是实验系统
本身的执行稳定性问题。一个诚实的 benchmark 记录，必须把这种边界写出来，而不是只报“成功
样本”。

## 这次重构最后留下来的，不是一个脚本，而是几条更重要的规则

回头看这轮工作，真正重要的成果并不是某个具体 runner 文件，也不是某个 JSON schema，而是
下面几条规则终于稳定了：

第一，测试资产必须从“人能手工跑”升级成“程序能统一跑”。
第二，公开任务输入和隐藏正式评测必须严格分离。
第三，功能测试和负例测试可以共享同一种最小 case 结构。
第四，benchmark 的输入池必须按可重复验证结果定义，而不是按历史印象定义。
第五，任务输入要尽量像真实开发起点，而不是像半公开答案。

这些规则一旦稳定下来，后面的事情就从“定义混乱”转成了“继续扩展样本和吞吐”。这两者差别很
大。前者意味着系统还没立住，后者意味着主干已经成立。

## 结尾：这次工作本质上是在修 benchmark，不是在修脚本

如果只用一句话总结，这次重构做的事情是：

把一批局部可用的 mock 测试，整理成了一条面向 driver generation 的 benchmark 链。

这条链包括：

- 最小化的 runtime case 格式
- 统一的 runner
- 可批量汇总的 summary
- 稳定定义的输入池
- 清晰分层的 env / eval / public
- 面向 solver 的 task_brief + datasheet 输入模型

它还没有把所有问题都解决掉，比如批量任务构造的吞吐还会受 provider 波动影响。但最难的部
分已经不是“这件事到底该怎么定义”，而是“怎样把已经定义清楚的流程继续扩展下去”。

对一个 benchmark 来说，这已经是很关键的一步了。
